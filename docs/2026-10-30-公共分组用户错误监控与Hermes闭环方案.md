# 用户分组错误监控与 Hermes 闭环调研及需求

> 调研日期：2026-10-30  
> 项目：Sub2API Upstream Console（6060 上游聚合控制台）  
> 状态：调研完成，需求待实施

## 一、调研情况

### 1. Sub2API 错误接口可用

自有 Sub2API 站点提供管理员运维接口，管理员 API Key 通过请求头 `x-api-key` 认证：

- `GET /api/v1/admin/groups`：读取分组列表；分组带有 `is_exclusive` 属性，可以区分公共分组和专属分组。
- `GET /api/v1/admin/ops/request-errors`：查询用户请求错误。
- `GET /api/v1/admin/ops/request-errors/:id`：读取单条错误详情。
- `GET /api/v1/admin/ops/request-errors/:id/upstream-errors`：读取该请求关联的上游错误尝试。

错误记录目前可提供：

- 用户实际收到的 `status_code`；
- 本地错误分类：`phase`、`type`、`error_owner`、`error_source`；
- 本地错误消息；
- `upstream_status_code`、`upstream_error_message`、`upstream_error_detail`；
- `upstream_errors` 中保存的多次上游尝试、状态码、阶段和错误正文；
- 分组、请求和错误记录标识。

“完整上游报错”的口径是 Sub2API 已记录并脱敏、截断后的完整可用内容。若目标站点没有记录某段上游正文，控制台无法凭空恢复原始内容。

### 2. 当前控制台可以复用现有能力

项目已经具备自有站点连接、运行时调度、SQLite 设置与加密存储、告警去重，以及 PushPlus 和 SMTP 双通道通知能力。新增功能可以挂接到这些现有模块，不需要另建一套通知系统。

### 3. 本机 Hermes 的通信现状

本机 Hermes Gateway 当前提供本地 Webhook，默认入口形态为：

```text
http://127.0.0.1:8644/webhooks/<name>
```

该入口支持 HMAC 签名校验，并可在处理完成后通过 `deliver=weixin:<目标>` 使用本机微信 Gateway 汇报结果。

服务器部署后，服务器上的 `127.0.0.1` 只代表服务器本身，不能直接访问本机 Hermes。因此，控制台不能把本机 Webhook 地址直接写进服务器配置。

推荐的通信方式是：

1. 本机主动向服务器建立持久的反向 SSH 通道；
2. 将服务器回环地址上的一个专用端口转发到本机 `127.0.0.1:8644`；
3. 服务器上的控制台只向服务器回环地址发 HMAC Webhook 请求；
4. 请求通过反向通道抵达本机 Hermes；
5. Hermes 完成后仍由本机微信 Gateway 向本人汇报。

这样不需要把 Hermes 端口暴露到公网。反向通道断开时，控制台应保留失败状态并重试；PushPlus 和邮箱告警不能依赖 Hermes 通道是否在线。

如果服务器无法接受反向 SSH 通道，再评估 Tailscale/同类私网或带身份校验的 HTTPS 中继。直接把 Hermes 端口暴露到公网不作为默认方案。

## 二、已确认需求

### 1. 监控范围

- 监控对象是用户自己的 Sub2API 站点，使用管理员 API Key。
- 控制台可以选择需要监控的具体分组。
- 公共分组和专属分组都必须支持，不能只筛选 `is_exclusive=false`。
- 每条错误记录必须保留站点、分组、错误 ID 和发生时间，按站点 ID + 错误 ID 去重。

### 2. 错误信息

发现用户请求报错后，获取并保存：

- 用户响应状态码；
- 本地报错分类和消息；
- 上游状态码；
- 上游错误消息和详情；
- Sub2API 已保存的完整 `upstream_errors` 数组。

详情接口取数失败时，必须标记为部分详情，不能伪装成完整错误。

### 3. 错误码分流

错误码列表可配置：

- `hermes_codes`：命中后交给 Hermes；
- `manual_codes`：命中后由本人处理。

匹配范围包括本地分类、用户状态码、上游状态码，以及已记录上游错误中的结构化错误码。同一条错误同时命中两组时，`manual_codes` 优先。

未命中任何列表的错误只记录并在控制台展示，不自动调用 Hermes，也不发送外部通知，除非后续另设开关。

### 4. Hermes 调用

- 代码只预留一个可配置的 `HERMES_PROMPT`，具体内容由用户填写。
- 发给 Hermes 的内容必须是：`HERMES_PROMPT` + 本次具体错误信息，错误信息包含上游报错。
- 控制台不设置 Hermes 权限，不限制 Hermes 的处理动作，也不代替 Hermes 做权限判断。
- Payload 不得包含管理员 API Key、用户 Token、代理密码或其他无关凭据。
- 服务器调用本机 Hermes 时，必须使用前述反向通道和 HMAC 校验；通信地址、专用端口、密钥和重试参数都应可配置。

### 5. 通知

命中 `hermes_codes` 时：

- 立即通过 PushPlus 和邮箱通知：“问题已产生并已移交 Hermes 处理”；
- 通知包含站点、分组、错误码、用户状态码、上游状态码、时间和事件 ID；
- 同时将错误事件提交给 Hermes。

命中 `manual_codes` 时：

- 不调用 Hermes；
- 直接通过 PushPlus 和邮箱通知本人处理；
- 通知包含本地报错和上游报错摘要。

### 6. Hermes 完成后的汇报

- Hermes 处理完成后，通过本机微信 Gateway 向指定微信目标汇报处理结果；
- 汇报至少包含事件 ID、问题摘要、处理结果和仍需人工处理的事项；
- 微信投递结果需要记录。通道失败时保留待重试状态，不能把“已提交 Hermes”误报为“已解决”。

### 7. 运行与可靠性

- 监控轮询周期、回看时间窗口、请求超时、每轮详情数量、重试次数和退避时间可配置；
- PushPlus、邮箱、Hermes Webhook 和微信汇报分别记录投递状态；
- 同一错误不能因轮询重复触发；
- 服务器与本机之间的反向通道断开时，错误事件仍需落库，恢复后按状态重试；
- 管理员 API Key、Hermes HMAC 密钥和通知凭据必须加密或通过服务器环境变量注入，界面只显示掩码。

本文件只记录调研结果和需求，不代表已经修改代码、建立服务器到本机的通道或完成生产部署。
